# Layout-Corrector Training

This document records exact S0-S4 package/vendor training and evaluation agreement for RICO25 and PubLayNet. The evidence uses real LayoutDM-processed batches, the vendor's 16-worker loader semantics, and the frozen LayoutDM generator weights. It does not claim S5 full-run statistical reproduction; S5 is `not-yet-run (https://github.com/creative-graphic-design/design-generators/issues/426)` and requires a separate user decision.

Run commands from the repository root. Generated data, logs, checkpoints, prediction files, and evaluation inputs stay under `.cache/layout-corrector/` or the separate local LayoutDM cache.

## Install

The lockfile environment is the source of truth for CPU-only repository checks and tests. The required initial synchronization and lockfile check are:

```bash
UV_FROZEN=1 uv sync --all-packages --frozen
git diff --exit-code -- uv.lock
```

GPU evidence uses an audited runtime because the locked `torch 2.13.0+cu130` build cannot initialize on the verified host driver. The audited runtime uses Python `3.11.15`, `torch-2.8.0+cu128-cp311-cp311-manylinux_2_28_x86_64.whl` (`torch 2.8.0+cu128`, CUDA tag `cu128`, SHA-256 `039b9dcdd6bdbaa10a8a5cd6be22c4cb3e3589a341e5f904cbb571ca28f55bed`), and `torchvision-0.23.0+cu128-cp311-cp311-manylinux_2_28_x86_64.whl` (`torchvision 0.23.0+cu128`, CUDA tag `cu128`, SHA-256 `93f1b5f56b20cd6869bca40943de4fd3ca9ccc56e1b57f47c671de1cdab39cdb`). Torch `2.8.0+cu128` is the selected same-major audited build because the `2.11.0+cu128` wheel has no usable kernels on the verified host. The audited environment is outside the repository under the package cache, and its complete `uv pip freeze` output retains `file://` editable lines and has SHA-256 `915bb3b975274708f2f7c8d9aac6e506080a329337e13c7e8d1c09a24a6b5da8`.

```bash
LAYOUT_CORRECTOR_AUDIT_VENV=<audit-venv>
UV_FROZEN=1 uv venv --python 3.11 "$LAYOUT_CORRECTOR_AUDIT_VENV"
UV_FROZEN=1 uv pip install --python "$LAYOUT_CORRECTOR_AUDIT_VENV/bin/python" --index-url https://download.pytorch.org/whl/cu128 torch==2.8.0 torchvision==0.23.0
UV_FROZEN=1 uv pip install --python "$LAYOUT_CORRECTOR_AUDIT_VENV/bin/python" -e lib/laygen -e models/layout-dm -e models/layout-corrector
UV_FROZEN=1 uv -q pip freeze --python "$LAYOUT_CORRECTOR_AUDIT_VENV/bin/python" | sha256sum
```

The CUDA kernel smoke and package tests passed in the audited runtime before evidence generation. The package test command produced `58 passed, 25 deselected`; those counts are package-test cases, not training samples. CPU-only repository checks and ordinary member tests use the lockfile environment, not the audited runtime.


## Scheduler and Recipe Notes

The vendor entry point is `vendor/layout-corrector/bin/corrector_train.sh`, a Hydra recipe from the LayoutDM codebase. It trains the corrector with a frozen LayoutDM generator. The compared recipe uses AdamW with learning rate `5.0e-4`, betas `(0.9, 0.98)`, weight decay `0.1`, gradient clipping at norm `1.0`, batch size `64`, and `ReduceLROnPlateau` on `val_loss` with factor `0.5`, patience `2`, threshold `0.01`, and epoch cadence. The loader keeps the vendor's 16 workers for S1-S4 comparisons; the loader-stream evidence uses two batches per train, validation, and TEST split.

The frozen LayoutDM reference uses the importance-sampled corruption branch. S1 records corruption probabilities, timesteps, reconstructed tokens, logits, per-attribute BCE tensors, weighted BCE, and total loss before optimizer mutation. EMA is not part of this loop. The scheduler is applicable and is not stepped before the validation boundary. Both systems use `CUBLAS_WORKSPACE_CONFIG=:4096:8`, `torch.use_deterministic_algorithms=False`, `cudnn.deterministic=False`, and 32-bit arithmetic for the recorded GPU lockstep.

S0 records both systems initializing on the selected CUDA device with the same seed and no native initialization tensor divergence. The package follows the vendor's selected-device construction order. The static registration-order assertion compares the complete ordered parameter-name lists and pins the vendor's backbone-first order; parameter registration order affects the reduction order of `clip_grad_norm_`.

## Seed Policy

S0 static initialization uses seed `123`. S1-S3 use training seed `42975`; natural S3 runs draw randomness independently through each system's own production path, with no per-step RNG restore or injected shared random tensor. The synchronized S3 diagnostic restores model, optimizer, and RNG state at each optimizer boundary as a separate diagnostic layer. S4 loader and full TEST evaluation use evaluation seed `314159`, with the vendor's 16-worker loader retained for the loader-stream check.
